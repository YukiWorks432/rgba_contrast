# 色空間モードと軸別ガンマ補正の仕様案

2026-10-30 時点の設計資料。数式と入出力の方針を実装し、ホスト上の表示・アルファ表現と旧プロジェクトの復元は実機確認を待つ。

RGB に HSL / HSV / YUV / OKLab / OKLch を加え、選択した色空間の各軸とアルファに、コントラストと独立したガンマ補正を設ける。色変換には `palette` を第一候補とし、YUV の行列変換、HSL 順変換の数値安定化、調整曲線はこのプラグインで定義する。

利用者が確認した条件は、H を含むすべての軸を調整対象とすること、初版は sRGB・Rec.709 とその線形版を優先することの二点。それ以外の数式、範囲、表示方法は本資料の提案であり、未採用の事項を含む。

追加の検討依頼を受け、HSL は SDR 範囲、HSV は非負の HDR 範囲として定義し、色調整を行うときに入力をその範囲へ制限する案を推奨する。半透明では色と不透明度を分離して調整する。制限による値の消失、無調整時の保持、アルファ 0、既存プロジェクトの扱いを以下に具体化した。ホスト別の画素表現は実機確認前であり、対応済みとは扱わない。

## 現行実装とリファクタリングの前提

初回調査は `693bdc4` を対象とした。その後、[PR #5](https://github.com/YukiWorks432/rgba_contrast/pull/5) が `develop` に取り込まれ、現行コードは `src/contrast.rs`、`src/pixels.rs`、`src/lib.rs` に分割された。Modern は既存のシグモイド曲線を維持し、数値安定性と整数への丸めを修正している。`Mode` は `Modern = 1` / `Legacy = 2` というコントラスト方式であり、新しい色空間選択とは独立して残す。

後続のリファクタリングでは、描画経路、Premiere の画素形式、HDR やアルファの契約を整備する。本機能はその契約が確定した版を基点とする。本資料の提案と既存実装が異なる場合、実装前に改めて差分を確認する。PR #5 の HDR 範囲外における逆関数は、従来の範囲制限を引き継いでいる。

リファクタリングには、Adobe に依存しない一軸の曲線処理、色の三成分とアルファを区別した画素処理、画素形式の入出力、Adobe のパラメーター取得という境界があればよい。将来の色空間ごとの型階層や汎用的な変換経路探索まで先に導入する必要はない。

## 操作と既定値

| 項目 | 提案 |
| --- | --- |
| 色空間 | RGB / HSL / HSV / YUV（BT.709）/ OKLab / OKLch。既定値は RGB |
| コントラスト方式 | 現行の Modern / Legacy を維持。H のみ後述の周期曲線を使う |
| 軸ごとのコントラスト | 三軸とアルファ。それぞれ既定値 0、範囲 −100〜100 |
| 軸ごとの基準値 | コントラストの基準。符号付き軸では中央が無彩色の 0 に相当する |
| 軸ごとのガンマ | 三軸とアルファ。それぞれ既定値 1.00、入力可能範囲 0.10〜10.00、通常のスライダー範囲 0.25〜4.00 |
| 色相ガンマの起点 | H があるモードで使用する角度。既定値 0°。H のコントラスト基準とは区別する |
| 入力 RGB の解釈 | sRGB / Rec.709 Gamma 2.4 / Rec.709 伝達関数 / 線形 sRGB・Rec.709。RGB モードは従来どおり作業用 RGB 値を直接調整する |
| 色と不透明度を分離 | 色をアルファ未乗算の状態で調整する。新規適用・リセット時はオン、項目のない既存プロジェクトを開いたときはオフ。非アニメーション設定 |

三つの操作枠は下表の軸名へ切り替える。値とキーフレームは枠に保持し、モード切り替えで初期化しない。異なる色空間で同じ数値が同じ見た目になることは保証しない。初版の色空間選択と入力 RGB の解釈は、アニメーションさせない設定を推奨する。

| 色空間 | 第1軸 | 第2軸 | 第3軸 | 主な用途 |
| --- | --- | --- | --- | --- |
| RGB | R | G | B | 現行の色チャンネルごとの調整 |
| HSL | H：色相 | S：彩度 | L：明度 | HSL の彩度と明度を分けた調整 |
| HSV | H：色相 | S：彩度 | V：明度 | HSV の彩度を保った明るさ調整 |
| YUV（BT.709） | Y′：明るさ信号 | U：青の色差 | V：赤の色差 | 明るさ信号と色差の分離 |
| OKLab | L：知覚的な明るさ | a：緑−赤 | b：青−黄 | 知覚的な明るさと対向色の調整 |
| OKLch | L：知覚的な明るさ | C：クロマ | h：色相 | クロマ・色相を保った明るさ調整 |

OKLab の a/b を個別に調整すると、色相も変化する。OKLch の C はクロマであり、HSV/HSL の彩度と同じ量ではない。軸値の保持と、出力時の色域制限後の見た目の保持も区別する。[Oklab の原著](https://bottosson.github.io/posts/oklab/)

## ガンマと処理順

「色と不透明度を分離」がオンの処理順は「画素の読み取り → 必要な場合だけアルファ乗算を解除 → モードの入力範囲へ制限 → 色空間変換 → 各軸のコントラスト → 各軸のガンマ → 入力と同じ RGB 表現へ逆変換 → 必要な場合だけ出力アルファを乗算 → 画素の書き込み」に固定する。RGB / YUV / OKLab / OKLch では、この入力範囲の制限を行わない。アルファは別の一軸としてコントラスト、ガンマの順に処理し、色空間変換には含めない。オフではアルファの乗算解除と掛け戻しを省略し、受け取った色の三成分を直接処理する。

通常の非負軸には次の曲線を使う。`s` は調整量の基準スケールであり、色域の上限ではない。

```text
G(x, γ, s) = s × (x / s)^(1 / γ)
```

R/G/B、HSL の S/L、HSV の S/V、Y′、OKLab/OKLch の L、アルファは `s = 1`。OKLch の C は `s = 0.4` を提案する。`γ = 1` は計算を省略して元の値を返す。0 と基準値 s は変わらない。`0 < x < s` では γ > 1 で値が増え、γ < 1 で減る。`x > s` では増減が逆になる。

新しい色空間では、コントラスト後の S と HSL の L を 0〜1、HSV の V と OKLch の C を 0 以上に収めてからガンマをかける。これは各軸の定義上の範囲であり、RGB へ戻した結果が表示可能な色域に入ることを保証しない。追加するアルファガンマは γ ≠ 1 の場合に 0〜1 を対象とする。γ = 1 の既存アルファ処理の範囲規則は、リファクタリング側の契約を維持する。

例として、明るさ 0.25 は γ = 2 で 0.5、γ = 0.5 で 0.0625 になる。これは利用者による階調調整であり、入力 RGB の伝達関数を復号する処理とは別に扱う。

### 符号を持つ軸

U/V、a/b、および範囲外の負の RGB/Y′/L 値を許す経路では、符号を保存して絶対値にガンマを適用する。

```text
G_signed(x, γ, s) = sign(x) × s × (abs(x) / s)^(1 / γ)
G_signed(0, γ, s) = 0
```

U/V は `s = 0.5`、a/b は `s = 0.4`。例えば U = −0.125、γ = 2 なら −0.25 になる。無彩色の 0 が移動せず、負数への非整数乗による NaN を避けられる。

符号付き軸を単純に 0〜1 へずらしてから通常のガンマをかける方法は採用しない。無彩色に対応する中央の値まで移動し、ガンマだけで色かぶりが生じるためである。

コントラストへ渡すときは `u = (x / s + 1) / 2` として、基準値 50% を色差 0 に対応させる。ガンマは元の符号付き座標に戻してから適用する。a/b と C の 0.4 は CSS Color 4 の百分率の基準を参考にした操作上のスケールであり、±0.4 や 0.4 で強制的に切り詰めない。[百分率と軸の定義](https://www.w3.org/TR/css-color-4/#specifying-oklab-oklch)

### 色相 H/h

色相ガンマは起点 h₀ から一周を 0〜1 に正規化し、ガンマを適用して角度へ戻す。

```text
u = mod(h − h₀, 360) / 360
h_out = mod(h₀ + 360 × u^(1 / γ), 360)
```

`mod` は負数にも対応する非負の剰余とする。起点 0°、γ = 2 なら 90° → 180°、180° → 約254.56°となる。0°と360°は同じ色相なので、円周上の出力は境目で連続する。ただし傾きは境目で一致するとは限らず、起点近くの色分布の伸縮は意図した効果として扱う。HSL/HSV と OKLch では、同じ角度が同じ色を表すとは限らない。

H のコントラストには、既存の直線式をそのまま適用しない。例えばゲイン 0.5、基準値 0.5 では、一周の両端が 90°と270°になり、隣接する入力色相が不連続になる。

専用の周期曲線として、次式を候補とする。c は −100〜100、p はコントラストの基準角である。

```text
a = c / 100
h_contrast = mod(h + (180 / π) × a × sin((π / 180) × (h − p)), 360)
```

この式は c = 0 で無調整、p とその反対側の角度を保存し、一周全体で連続する。角度に対する傾きは `1 + a × cos((π / 180) × (h − p))` で非負になるため、色の並び順も反転しない。三角関数には上式のとおり角度をラジアンへ変換して渡す。H では Modern/Legacy の選択にかかわらずこの曲線を使う案であり、その例外は操作説明へ記載する。強さの感じ方は参照画像で評価してから確定する。

無彩色では H が定まらない。彩度またはクロマが 0 のままなら、H の操作で色を付けない。コントラスト操作によって無彩色から彩度・クロマを増やす場合は、元の H を 0°とする規則を提案する。前の画素や前のフレームから H を借用しない。

完全な無彩色入力では、色変換後の色差・彩度・クロマを正確な 0 として扱う。変換の丸め誤差を大きなガンマ値で増幅し、無彩色に色が付くことを防ぐ。近い色を広い固定しきい値でまとめて無彩色へ落とす処理は加えない。

## 入力 RGB、YUV、範囲外値

### 入力の色管理

初版の対象である sRGB と Rec.709 は同じ原色と D65 白色点を使うため、主な違いは伝達関数になる。ただし Rec.709 の伝達関数と Gamma 2.4 は区別する。単なる「線形 / 非線形」の二択では復号方法を特定できない。

新モードの計算基準は、HSL/HSV が符号化済み sRGB、YUV が BT.709 の伝達関数で符号化した RGB、OKLab/OKLch が線形 sRGB とする案を推奨する。入力の解釈に従って線形 RGB へ復号し、各モードの計算基準へ変換する。調整後は元の入力表現へ戻す。HSV の彩度保持は、この計算基準上で保証する。

入力 RGB の解釈は、初版では明示的な選択を推奨する。sRGB を既定とする場合も、Adobe の設定を自動判別したという表示にしない。AE の作業用色空間と線形化設定、Premiere の色管理を取得・反映できることが実機で確認できた段階で、自動選択を検討する。`palette` 自体は Adobe の現在の設定を取得しない。[Adobe の作業用色空間と線形化](https://helpx.adobe.com/after-effects/desktop/adjust-colors/color-management/color-management.html)

ACEScg、任意の ICC プロファイル、OCIO 設定の一般対応は今回の優先範囲に含めない。sRGB・Rec.709 への対応と、各調整モードが負値・1を超える値を保持することは別の契約とする。HSL/HSV の制限は次節に示す仕様上の提案であり、入力 RGB の解釈を選んだだけで全モードの範囲外値を破棄しない。

### YUV の定義

YUV という名称だけでは、行列、信号範囲、色差のスケールが決まらない。今回は BT.709 の Y′CbCr を浮動小数点で扱う方式を推奨する。UI では「YUV（BT.709）」とし、U = Cb、V = Cr であることを説明する。アナログ YUV が目的なら、係数を別途選び直す。

```text
Y′ = 0.2126 R′ + 0.7152 G′ + 0.0722 B′
U  = (B′ − Y′) / 1.8556
V  = (R′ − Y′) / 1.5748

R′ = Y′ + 1.5748 V
B′ = Y′ + 1.8556 U
G′ = (Y′ − 0.2126 R′ − 0.0722 B′) / 0.7152
```

通常範囲は Y′ = 0〜1、U/V = −0.5〜0.5、無彩色の U/V = 0。プラグイン内部では信号範囲を狭める符号化、整数への量子化、色差の間引きを行わない。Y′だけの操作は色差を保持するが、HSV の彩度や知覚上の彩度を固定する操作とは異なる。[ITU-R BT.709-6、信号形式](https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.709-6-201506-I!!PDF-E.pdf)

### 32bit の範囲外値と色域

RGB / YUV / OKLab / OKLch は、途中の RGB を一律に 0〜1 へ切り詰めない方針を推奨する。OKLab の変換には実数の立方根を使い、負数に対する `powf(1.0 / 3.0)` で代用しない。アルファは色と区別し、前述のアルファガンマと既存処理の規則に従う。

8/16bit への書き込みでは表現可能範囲への制限と量子化が必要であり、色域外の結果に対して色相・彩度の保持までは保証しない。32bit では、そのモードの処理を経て残った色域外値を後段へ渡す。HSL/HSV の入力制限で失われた値は復元しない。初版の自動色域圧縮は追加しない。[Palette の色域と切り詰めの説明](https://docs.rs/palette/latest/palette/struct.Oklab.html#clamping)

### HSL/HSV の負値・HDR 入力

初版は次の範囲に固定する。範囲制限は、色を実際に調整する経路だけで行う。色の調整なし・アルファのみの場合の例外は次節で定義する。

| モード | 変換前の RGB | 軸の範囲 | 範囲外値への効果 |
| --- | --- | --- | --- |
| HSL | 各成分を 0〜1 に制限 | H は一周、S/L は 0〜1 | 負値と 1 を超える明るさを失う。SDR 用途とする |
| HSV | 各成分の負値を 0 に制限。上限は設けない | H は一周、S は 0〜1、V は 0 以上で上限なし | 負値は失う。非負 RGB の HDR を扱える |

「色と不透明度を分離」がオンなら、範囲を判定する対象はアルファ未乗算の色である。例えば RGB = (0.5, 0.25, 0.125)、アルファ = 0.25 が乗算済み形式で渡された場合、色は (2, 1, 0.5) なので HSL では制限の対象になる。乗算済み RGB が 0〜1 に入ることを SDR の判定に使わない。

対象の入力表現はいずれも、非負側で単調かつ黒 0・基準白 1 を共有する。そのため、上の制限を入力 RGB の表現で先に行い、その後で符号化済み sRGB へ変換する。これにより、HSL/HSV のために負値へ伝達関数のべき乗を適用する必要がない。これは入力表現と計算基準で制限の位置が同じになる今回の対応範囲に限った規則である。

非負 RGB に対する HSV は、最大成分 M、最小成分 m として V = M、M > 0 なら S = (M − m) / M とする。V > 1 でもこの定義を使える。RGB = (1.5, 0.5, 0.5) に V の γ = 2 を適用すると、約 (1.224745, 0.408248, 0.408248) となり、H = 0°、S = 2/3 を保つ。V を 1 に切り詰める変換 API は使用しない。

HSL では L = (M + m) / 2、彩度の分母は通常範囲で 1 − |2L − 1| となる。未制限の (1.5, 0.5, 0.5) は L = 1、色差は 1 なので分母が 0 になる。提案仕様では先に (1, 0.5, 0.5) に制限するため H = 0°、S = 1、L = 0.75 となり、L の γ = 2 の出力は約 (1, 0.732051, 0.732051) になる。元の 1.5 は保持されない。

範囲内でも白付近の桁落ちに注意する。HSL の順変換では、Δ = M − m が 0 なら H/S = 0 とし、Δ > 0 では次の等価な分母を使用する。中間計算は f64 とし、H と L は通常の定義に従う。

```text
D = M + m                    （M + m <= 1）
D = (1 − M) + (1 − m)        （M + m > 1）
S = Δ / D
```

M = 1、m = 1 − 2^-24 は f32 で表現できるが、f32 の `2 − (M + m)` は加算の丸めによって 0 になる。この具体例があるため、HSL の順変換をクレート任せにはしない。ローカルの `palette 0.7.7` と確認時の上流実装は負の RGB を 0 にし、上半分では `2 − (M + m)` を使う。`FromColorUnclamped` という名前だけで、範囲外値の保持やこの境界での数値安定性を保証したと判断しない。[Palette の HSL 実装](https://raw.githubusercontent.com/Ogeon/palette/master/palette/src/hsl.rs)

符号付きの独自 HSL/HSV は初版に導入しない。比較した OpenColorIO の拡張 HSV も、RGB = (1, 0, −1) を V = 0、S = 2 とし、逆変換側では S を 1.999 に制限するため、この例を可逆には扱えない。「既存の拡張実装を採用すれば、すべての負値を保持できる」とは言えない。[OpenColorIO の変換実装](https://github.com/AcademySoftwareFoundation/OpenColorIO/blob/main/src/OpenColorIO/ops/fixedfunction/FixedFunctionOpCPU.cpp)

範囲外の画素だけを無調整に戻す方式は、色を調整した範囲内の画素との境界で不連続になり得るため採用しない。画素ごとに最大値を 1 へ正規化してから処理する方式も、非負 HDR で HSV の V が常に 1 になり、V のガンマが効かなくなるため採用しない。制限分を別途足し戻す方式も、意図した色相・彩度の操作と残差の色が食い違うため採用しない。

操作説明には「HSL：色調整時は RGB を 0〜1 に制限」「HSV：色調整時は負の RGB を 0 に制限、HDR の明るさは対応」と表示する。負値を保つ作業では RGB / YUV / OKLab / OKLch、色相・クロマを分けた調整では OKLch を案内する。これらも任意の RGB 色域や HDR 表示規格への色管理対応を意味しない。

### 無調整とアルファだけの操作

色の三軸すべてでコントラスト = 0、ガンマ = 1 なら、入力範囲の制限・色空間変換を省略する。基準値や色相ガンマの起点だけを変更しても、対応する調整量が無調整ならこの条件を維持する。

アルファも無調整なら、元の画素をそのまま返す。負値、HDR、アルファ 0 の RGB を含め、モード選択だけでは値を変えない。アルファだけを調整するときも色空間変換は行わず、後述の形式に応じた掛け戻しだけを行う。アルファの計算結果も入力と同じなら、この掛け戻しも省略する。

この規則には明示すべき制約がある。HSL/HSV の範囲外画素は、色のガンマを 1 からわずかに動かすだけでも入力制限が始まるため、無調整状態との間で出力が飛ぶことがある。無調整での完全保持と、調整中の標準 HSL/HSV の範囲制限を両立させた結果であり、全設定を通した連続性は保証しない。この用途で連続したアニメーションが必要なら、範囲外値を扱える別モードを使う。

### 半透明とアルファ 0

処理の基準となる色 C は、アルファを乗算していない RGB とする。素材ファイルの読み込み設定から、プラグインへ渡された画素の表現を推測しない。ホストとの接続部分が、各描画経路の画素を未乗算か乗算済みかに分類する。画素の値や拡張子からの自動推定は行わず、利用者にホスト内部の形式を選ばせる項目も作らない。

「色と不透明度を分離」がオンの場合、a を入力アルファ、a_out をコントラスト後にガンマを適用した出力アルファ、F を選択モードの色調整とすると、0 < a <= 1 の処理は次のとおり。

```text
未乗算の入出力: C = RGB_in          → RGB_out = F(C)
乗算済みの入出力: C = RGB_in / a    → RGB_out = a_out × F(C)
```

乗算済みの場合も、入力の色を取り出す除数は元の a とする。変更後の a_out で割らない。伝達関数の変換とアルファ乗算の順序もホストの画素契約に合わせ、元の RGB 表現へ戻してから、出力形式が要求する位置で一度だけ掛け戻す。未乗算のバッファには、割り算も掛け戻しも行わない。

この規則では、同じ C で a だけが違う画素は、色調整後も同じ未乗算の色になる。例えば C = (0.8, 0.2, 0.1)、a = 0.25 の乗算済み RGB は (0.2, 0.05, 0.025)。アルファの γ = 2 のみを適用すると a_out = 0.5、RGB_out = (0.4, 0.1, 0.05) となり、色 C は変わらない。「アルファだけの操作では RGB の格納値が絶対に変わらない」という契約にはしない。

| 条件 | 推奨する扱い |
| --- | --- |
| 未乗算で a = 0 | 隠れた RGB を有効な色として扱う。色が無調整なら保持し、色を調整するなら同じ F を適用する。後でアルファが増えた場合もこの色を使う |
| 乗算済みで a = 0、a_out = 0 | 除算しない。色は復元不能なので色調整を省略し、渡された隠れた RGB をそのまま保持する |
| 乗算済みで a = 0、a_out > 0 | 未乗算の元の色は復元できないため C = 0 を起点に F を適用する。隣接画素からの色補完は行わない |
| 乗算済みで a > 0、a_out = 0 | 出力 RGB = 0。変換後の未乗算色を別の記憶領域へ保存する仕組みは作らない |
| 非常に小さい a > 0 | 固定しきい値で 0 に落とさず、元の a で除算する。乗算解除・掛け戻しの中間は f64 とし、低ビット深度で既に失われた色は復元できないことを区別する |

完全無調整の画素コピーを、この表より優先する。アルファ 0 からの可視化は主に Legacy のコントラストで発生し、通常の正のガンマだけでは 0 は増えない。アルファの範囲外値・非有限値の扱いはリファクタリングで決める入出力契約に従い、本表の 0〜1 の契約と混在させない。HDR では未乗算 RGB が 1 を超え得るため、乗算済み RGB を常にアルファ以下へ制限する処理は追加しない。

AE の `preserve_rgb_of_zero_alpha` の伝播、アルファ 0 を可視化する経路の `PF_OutFlag2_REVEALS_ZERO_ALPHA`、描画範囲の計算をこの契約へそろえる。上流の描画や素材読み込みで既に失われた隠れた RGB の復元は保証しない。[SmartFX の透明画素と描画範囲](https://ae-plugins.docsforadobe.dev/smartfx/smartfx/)

Adobe SDK の GLator サンプルは、AE の ARGB 入力を GPU 合成の前に乗算し、ホストへ返す前に乗算解除している。対応する AE 経路はこのサンプルに合わせて未乗算として扱う。Premiere の SDK は乗算済みの BGRP/PRGB 系を別形式として定義しており、今回の BGRA は未乗算として扱う。現在の形式宣言や AE の画素構造体名だけから、すべての経路が同じ表現だとは断定しない。実装時は AE の通常描画・SmartFX、Premiere の対応する形式ごとに、既知の色とアルファを渡して入力バッファと合成結果を確認し、入出力契約へ記録する。未確認の経路を対応済みに含めない。[Premiere の画素形式](https://ppro-plugins.docsforadobe.dev/universals/pixel-formats-and-color-spaces/)

### 既存プロジェクトとアルファ処理の互換性

色と不透明度の分離を RGB だけ除外すると、色空間を切り替えたときに半透明の色が不統一になる。一方、既存の RGBA 独立処理を無条件に置き換えると、乗算済みの経路で従来の結果が変わる。このため「色と不透明度を分離」を一つの保存可能な設定として追加し、全モードに共通で適用する案を推奨する。

新規適用とリセットはオン。設定が存在しない既存プロジェクトはオフとして、RGB と全ガンマ 1 でリファクタリング後の結果を保つ。オフは、受け取った RGBA の成分を独立に処理する動作として説明する。ホストの形式を切り替える設定とは区別する。操作途中でガンマが 1 かどうかを見てアルファ処理方式を切り替えない。

導入済み SDK の `AE_Effect.h` と `after-effects 0.2.1` に `PF_ParamFlag_USE_VALUE_FOR_OLD_PROJECTS` が存在する。このフラグで既存プロジェクトの不足パラメーター用の値をオフ、新規適用用の既定値をオンに分ける。AE/Premiere の既存プロジェクト・プリセットで復元結果を確認してから採用する。確認できないホストについて、暗黙に新しいアルファ処理へ移行させない。

## 使用クレート

| 候補 | 判断 |
| --- | --- |
| `palette 0.7.7` | 第一候補。HSL/HSV/OKLab/OKLch と線形 RGB の型・変換をまとめられる。MIT OR Apache-2.0。HSL の順変換だけは上記の安定した式を使い、型と逆変換を利用する。HSV は V > 1 を途中で切り詰めない変換を使う |
| `color 0.3.3` | 比較候補。CSS Color 4 を中心とした型・変換を提供するが、今回必要な HSV/YUV を標準型だけでそろえられない |
| `colorutils-rs` | SIMD による画像変換を重視する候補。現状の一画素処理へ導入する利益は未測定。今回の第一候補にはしない |
| `yuv 0.8.19` | 画像形式や色差間引きを伴う変換向け。今回の三成分の浮動小数点行列だけのためには導入しない |

依存指定案は次のとおり。実装時には公開版と変更履歴を再確認して Cargo.lock に解決結果を固定する。

```toml
palette = { version = "0.7.7", default-features = false, features = ["std"] }
```

名前付き色、乱数、シリアライズ、SIMD 用の追加機能は初版では不要。YUV の往復行列、HSL 順変換の安定化、符号付きガンマ、周期的な色相調整、アルファの分離には専用クレートを追加しない。通常のべき乗や三角関数は Rust 標準ライブラリを使う。OpenColorIO は比較資料として参照したもので、今回の依存には追加しない。

採用の根拠は [Palette の型と機能](https://docs.rs/palette/0.7.7/palette/)、[color の対象範囲と型一覧](https://docs.rs/color/latest/color/)、[colorutils-rs の説明](https://github.com/awxkee/colorutils-rs)、[yuv の API](https://docs.rs/yuv/latest/yuv/) を確認した。性能比較や Adobe 実機での互換性を検証済みという意味ではない。

## 実装境界と互換性

色変換、軸の調整、入力 RGB の解釈を小さな独立部分として追加し、リファクタリングで確定した一画素処理へ接続する。現在の `src/contrast.rs` の曲線処理と `src/pixels.rs` の画素処理を踏まえ、リファクタリング後の構成に色変換とガンマを接続する。パラメーター登録とホスト別走査の実際の配置は、後続のリファクタリング完了後に決める。アルファを色変換クレートへ渡す必要はない。

レンダー開始時に入力設定を型へ変換し、ガンマの逆数、基準スケール、コントラスト係数、無調整判定を準備する。画素ごとに Adobe のパラメーターを取得しない。画像全体の変換用バッファや、Adobe の並列描画に重なる独自のスレッドプールは追加しない。

現行 `after-effects 0.2.1` の `Parameters::param_id` は、`Params` の Debug 表現をハッシュ化して保存 ID を作る。したがって既存の `Params::Red` などを `Axis1` へ単純に改名してはいけない。既存 ID、パラメーター型、Mode の選択値、エフェクトの識別名、既存パラメーターの位置を維持し、新しい設定は追加する。UI 上の表示名変更と、保存 ID の変更を分ける。

受け入れの基点はリファクタリング後の修正版。既存プロジェクトは、RGB・全ガンマ 1・色と不透明度の分離オフで、その基点と同じ結果になることを確認する。新規適用では色と不透明度の分離をオンとするため、乗算済みの経路でコントラストを調整した結果は従来と異なり得る。全調整が無調整の場合は、どちらの設定でも元の画素を保持する。旧プロジェクト、プリセット、キーフレーム、式からの参照についても Adobe 上で確認する。

## 検証と残る判断

検証はプラグイン全体が保証する振る舞いを対象とし、外部クレートの関数だけを呼び直すテストにしない。期待値には規格の例、手で求められる値、独立した参照計算、調整前後の不変条件を使う。

- 全モードの無調整で、負値・1を超える値・透明部分を含む画素が変わらない。
- 軸を一つだけ調整し、同じ計算基準の色空間で他軸が許容誤差内で保たれる。アルファの独立性も確認する。
- HSV の V のみを調整したとき、色域制限が起きない範囲で H/S が維持される。例として RGB = (0.2, 0.1, 0.05)、V の γ = 2 は約 (0.447214, 0.223607, 0.111803) になり、S = 0.75 を保つ。
- U/V・a/b のガンマで 0 と符号が保存される。左右対称の入力に対して出力も左右対称になる。
- H/h の起点前後、360°の同値性、コントラストの色順保存、無彩色での振る舞いを確認する。色相の誤差は通常の引き算ではなく円周上の距離で測る。
- sRGB、Rec.709 の各伝達関数、線形入力を区別し、二重の線形化が起きないことを検証する。
- HSL の (1.5, 0.5, 0.5) と HSV の同じ入力を、本資料の独立した期待値で検証する。(-0.2, 0.4, 1.5) は、HSL で (0, 0.4, 1)、HSV で (0, 0.4, 1.5) を調整した結果と一致する。後者の V を 1 へ制限しない。
- HSL の黒・白・無彩色、(1, 1 − 2^-24, 1 − 2^-24)、0/1 の直前・直後の入力を確認する。白付近の例では S = 1 と有限の出力を期待し、単に NaN を最後に 0 に置き換えることで合格させない。色の無調整から調整へ移ったときの入力制限も、仕様どおりの変化として別に検証する。
- 同じ色 C と異なるアルファを持つ画素で、色調整後の未乗算の色が一致することを、未乗算・乗算済みの両形式から検証する。アルファは 1、0.5、0.25、1/255、1/32768、1e-6、0 を使い、形式の量子化誤差を区別する。
- アルファだけの操作で未乗算の色が保たれ、HSL/HSV の入力制限が実行されないことを確認する。本文の a = 0.25 → 0.5 の例と、HDR の C = (2, 1, 0.5) を含める。分離オフでは RGB の格納値を変えないことも、既存契約として検証する。
- アルファ 0 の隠れた RGB、0 から正のアルファへ変わる Legacy 設定、正から 0 になる設定を、透明画素の表の各条件に沿って検証する。32bit の小さな正のアルファを固定しきい値で消さないことと、隠れた RGB の要求が上流へ伝わることを確認する。
- 色と不透明度の分離について、保存項目のない既存プロジェクトはオフ、新規適用・リセットはオンとなり、保存し直した値が復元されることを確認する。
- AE の 8/16/32bit、半透明の境界、キーフレーム、複数フレームの並列描画、Premiere の実際に対応する描画経路で確認する。現行の Premiere 向け形式宣言だけで対応済みと判断しない。

リポジトリの既存検査は `cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test`。追加後の版で実行する。Rust の自動検査の実行結果は PR に記録する。Adobe 上での描画検証は未実施。本文の数値例は JavaScript の倍精度計算で確認し、白付近の f32 加算の丸めは `Math.fround` でも確認した。Rust 実装全体の精度や性能の検証は含まない。

HSL/HSV の入力範囲と半透明の計算方針は、本資料では上記を推奨案とする。H 専用コントラスト曲線と YUV の Y′CbCr を上記のとおり実装する。実装時の確認事項として、ホスト・描画形式ごとの実際のアルファ表現、新旧の既定値を分ける仕組みのホスト対応、リファクタリング後の入出力契約との整合を残す。これらは検証未実施であり、ホストでの挙動は検証済みとはしない。
